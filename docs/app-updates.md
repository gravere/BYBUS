# BYBUS 应用更新与发布

应用升级独立于游戏安装及零协汉化更新。发布仓库为 `gravere/BYBUS`。应用通过固定仓库 ID `1415176635` 查询公开的 GitHub Releases API，避免仓库改名影响检查与下载。

更新请求只接受该仓库 ID 对应的最新发行版与资源 API，以及 GitHub 的发行文件域名。界面中的网页入口使用当前仓库名称。无法通过应用内更新的旧安装包，可从最新 Release 下载完整 APK 覆盖升级。

## 更新路径

- 设置里的「更新」使用现有详情面板和返回层级，同页提供 BYBUS 与汉化更新；首页不等待此查询，游戏启动不依赖查询成功。两种更新仍使用各自的资源来源、工作线程和校验流程。
- 用户主动检查最新正式 Release。Release 附带 `bybus-update.json`，声明包名、显示版本、递增的内部版本、最低系统版本、APK 文件名、大小与 SHA-256。忽略草稿和预发布，通过内部 `versionCode` 判断新旧，不比较显示版本的字符串顺序。
- 元数据与下载都有超时、大小限制；仅允许固定 GitHub API 和 GitHub 官方 Release 文件域名，不把任意返回网址当可执行文件源。
- 下载到宿主独立缓存，流式计算 SHA-256；校验完整文件、实际包名、内部版本、最低系统版本和 APK 密码学签名。签名必须与当前 BYBUS 一致。下载失败不替换现有应用，不触碰容器数据。
- 使用限于单个升级缓存目录的 FileProvider 授予临时只读权限，交给 Android 系统确认覆盖安装。不会静默安装、卸载旧版或清除数据。用户拒绝后仍可重试；进程重建后不自动发起安装。
- FileProvider 的路径必须通过 Manifest 中的 `android.support.FILE_PROVIDER_PATHS` 元数据声明；静态 `getUriForFile` 不读取子类构造函数的资源参数。发行脚本核对最终 APK 中的元数据指向和 Provider 权限，防止下载成功后无法生成安装 URI。
- 同时保留「GitHub 发行页面」入口，网络失败时展示真实原因，不把查询失败写成已是最新版。
- 自动进入页面可复用一分钟内的成功结果；手动检查可主动刷新，不共用本地成功缓存与服务器限流的等待时间。仅 429，或具有剩余配额为零、有效 Retry-After / 限流错误消息的 403 记录服务器等待；普通 403、404、5xx 和网络失败不读取配额重置时间来锁住检查。
- 服务器等待在当前进程使用单调时钟，界面显示剩余时间并到期恢复检查按钮；重启后仅恢复有记录时间、范围合法且仍有效的服务器等待。升级清理旧 `retryAt` 字段，成功检查也清除持久等待，取消请求不写入等待状态。

## 增量下载

更新器支持可选的 `bybus-copy-v1` 差异补丁。已安装的更新器支持该协议且基准 APK 匹配时，才可使用增量下载；旧更新器无法完成更新时，下载最新完整 APK 覆盖升级即可。首次安装和手动更新始终使用完整 APK，`.delta` 文件不能独立安装。

- 元数据使用 schema 1 和 `BYBUS.apk`；可选的 `deltas` 数组最多声明三个旧版本。每项绑定旧构建号、旧 APK 大小和 SHA-256、补丁资源名称、大小、SHA-256 及格式。可选补丁信息不可用时保留完整更新能力。
- 检查更新的后台线程读取宿主自身 `ApplicationInfo.sourceDir`，核对旧 APK 大小和 SHA-256 后才展示增量下载量；不读取游戏 APK，不需要保留旧的下载文件。下载前再次核对基准文件。
- 补丁通过 GZIP 流保存有界的 COPY / DATA 指令。COPY 复用旧 APK 中逐字节相同的压缩数据区，DATA 携带新版字节。ZIP 头、签名块、中央目录和对齐字节都按原样恢复，禁止解压重打包或重新签名。解码器限制基准/目标大小、指令数量、偏移和输出总量，使用固定缓冲区，支持取消。
- 补丁下载完成须验证大小和 SHA-256；合成完整 APK 后须匹配发行版的 SHA-256，并继续执行 APK 签名、包名、构建号与最低系统版本验证。补丁不匹配或合成失败只回退一次完整下载；用户取消不触发回退，服务器限流时等待恢复，不立即回退并再次请求。界面展示下载、合成、回退及校验阶段。
- 缓存只保留当前目标 APK，补丁和未完成文件在成功、失败或取消后清理。增量减少网络下载量，合成和系统覆盖安装仍需要完整 APK 的临时空间。
- 发行脚本优先选取输出目录内最多三个较新的、构建号不低于 48 的已签名旧 APK，也可用 `--base-apk` 显式指定。只有签名一致、逐字节重建校验通过且补丁小于完整包的 80% 才随 Release 发布；否则只发布完整包。首次引入协议的构建 48 不发布无客户端可用的补丁。

格式细节与生成/回放验证见 `scripts/apk_delta.py` 和 `AppUpdateDelta.kt`。发布前使用实际签名 APK 做跨语言回放，不能仅凭模拟数据宣布增量可用。

## 发行文件与版本

| 文件 | 用途 |
| --- | --- |
| `BYBUS-<版本>-arm64-v8a.apk` | 带实际版本的完整安装包，首次安装和手动更新使用 |
| `BYBUS.apk` | 已发布更新器使用的固定名称；与上述安装包逐字节相同 |
| `bybus-update.json` | 应用更新元数据 |
| `BYBUS-update-<旧构建>-to-<新构建>.delta` | 可选差异补丁，仅供应用自动使用，不是安装包 |
| `SHA256SUMS.txt` | 全部安装包、差异补丁与更新元数据的 SHA-256 |

Release 标题采用 `BYBUS <版本>`。`app/build.gradle.kts` 是应用版本的唯一维护入口；界面版本资源由 Gradle 生成，发行脚本从实际 APK 读取版本并与配置核对，再生成文件名、标签、更新元数据和发行说明。

只修改 README、说明文档或发布工具，不需要调整应用版本或重新发布 APK。准备发布新的安装包时，再统一设置 `versionName` 并递增 `versionCode`；后者是更新器识别升级的依据。不要为每次源码提交升版，也不要复用已发布版本号覆盖旧安装包。

README、安装说明和反馈模板使用稳定入口或提示用户填写实际版本，不写死“最新版”的编号。历史验证记录与既有 Release 保留其真实版本和日期，不随新发布批量替换。

现有更新协议严格核对 `<版本>-build.<versionCode>` 标签和 `BYBUS.apk` 名称，保留该标签格式与兼容附件。改名不能破坏旧更新器；下载说明优先链接带版本的 APK，兼容附件在 GitHub 中标注用途。本地两种文件名尽量通过硬链接共用一份内容。

## 发布流程

1. 确定本次需要发布 APK 后，在 Gradle 中设置版本；在 `docs/release-notes.md` 只维护更新内容、验证范围和兼容说明，完成受影响功能的验证。
2. 使用 `scripts/prepare-release.py` 生成发行文件和输出目录中的 `release-notes.md`。版本标题、完整包链接和实际生成的补丁列表均由脚本填写，不在源码说明里手写。
3. 建立与源码提交对应的发布标签，上传完整 APK、元数据、校验文件及元数据中声明的补丁到草稿 Release；正文使用上一步生成的 `release-notes.md`。
4. 核对上传文件的大小与 SHA-256，再发布为正式版本。

已发布 APK 与标签不覆盖改写；文案与文件名调整可添加内容相同的下载别名，并更新校验清单。保留的发行版必须保持其更新元数据与兼容附件有效。

发行包保留最近三个正式构建。新版本上传、校验并正式发布成功后，再删除更早的 GitHub Release 及其附件，并清理本地对应版本 APK；保留的三个版本须完整可下载。清理不改写源码提交历史。旧版本仍可通过最新 Release 获取完整包，符合最新元数据基准的版本可使用差异补丁。

构建依赖由 `scripts/fetch-build-assets.py` 固定版本、大小与 SHA-256。完整构建步骤见[构建指南](building.md)。
