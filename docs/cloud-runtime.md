# 云端运行检查

`Android runtime inspection` 工作流在公开仓库的标准 Ubuntu runner 上运行，使用 Android SDK 官方镜像和 KVM。每个环境最多 20 分钟；截图、页面结构和诊断只保留 1 天，不上传 APK 副本。

在 GitHub Actions 中手动运行即可。工作流读取最新正式 Release，验证完整 APK 的大小、SHA-256 和固定 BYBUS 签名，再安装原始发行包。无需上传签名密钥、Google 账号或游戏资源。

`install-open` 模式在 Android 11 与 Android 17 官方镜像检查两类首页启动入口，以及系统
安装器实际确认和“打开”操作。候选版从前一正式版执行外部跨版本升级；独立临时应用仅
通过只读 ContentProvider 提供未经修改的签名 APK。随后用当前源码的较低内部版本 Debug
夹具调用生产安装入口，验证取消、再次安装、进程替换后的版本对账和首帧记录。该夹具
不是历史发行版，报告须分别标明两个来源；临时 APK 在正式发布前移除。

检查同时核对诊断导出的启动历史和退出阶段摘要；低版本系统明确报告 API 不可用。
`release-update` 用一个 Android 16 临时环境补查真实历史发行包的更新路径：安装上一正式版，
通过首页的设置、更新、下载、安装按钮升到当前正式版，再点击系统安装器的“打开”。
不使用较低版本号的新源码夹具，不修改应用的更新地址或注入更新状态。保留安装前的更新页，
检查系统安装器是否提前消失，以及打开后首页是否持续在前台。此用例仍没有用户容器数据，
不能把模拟器结果当作所有设备的结果；网络限流或界面条件缺失须明确报告。
`external-install` 单独检查完整 APK：由独立临时文件提供应用发起系统安装，分别覆盖首次安装
和同版本完整覆盖安装；BYBUS 不先经 ADB 或桌面启动。点击“打开”后检查首页持续可见，
不把安装成功、短暂首帧或随后手动启动算作通过。
`install-open-legacy` 只重跑 Android 11 的安装检查，避免因夹具差异重复其他已通过环境。
仅开发者的临时云端模拟器读取夹具结果，不连接用户设备，不启动游戏或操作账号。
这些结果不代表 vivo 安装器、OriginOS 7 或 70036 已验证；OEM 云真机须另有实际可用环境。

手动选择 `ui` 模式只检查界面，`runtime` 模式另含容器 Google 入口与实验镜像。勾选 `candidate` 时使用所选分支源码版本对应的签名发行草稿，验证后再公开同一安装包。GitHub 仅向有推送资格的凭据开放草稿，因此任务的临时令牌需要 `contents: write`；检查脚本只发起 GET 请求，不写入仓库或发布 Release。令牌不会保存，也不会随下载跳转转发。

`launch` 模式只检查启动控件与响应式首页。先运行正式 APK 并保存 README 原始截图，
再在云端安装同一源码的 debug 构建，通过仅存在于 debug 源集的页面绘制三种阶段、
大字体、深色及暂停动画状态。该页面调用生产控件，不执行准备、登录或启动游戏。
这些控件截图单独标记为渲染用例，不充当真实启动记录或 README 截图。草稿中临时使用的
`bybus-ui-probe.apk` 必须在发布前删除，正式 APK 不包含该页面。

`updates` 模式只覆盖更新页：正式 APK 的真实检查、取消、标签状态保留及导航条避让；
随后在独立 Debug 页面渲染共享更新卡片的下载、安装就绪、无更新、异常和汉化检查状态，
核对深色、大字体与平板布局。固定下载百分比仅属于明确标记的控件用例，不代表实际传输；
该页面没有下载或安装调用，也不进入 README 截图。

`repairs` 模式只验证全新容器的安装与账号服务注册：安装正式包后，覆盖同一源码的 debug
构建，在空账号服务缓存中静默安装内置 Google 组件，核对同一容器服务进程立即可查询到
Google authenticator。该探针不读取账号、不启动登录、不访问商品或付款，正式 APK 不含探针。
该模式还使用合成文件验证旧助手覆盖升级保留数据、签名权限拒绝 shell、生产流导入后摘要一致与源文件保留；随后移除夹具助手，安装固定哈希的上游正式 APK，检查两个应用能同时安装。目标夹具跳过真实游戏安装准备，因此不代表真实账号已迁移。只保留迁移界面证据，跳过平板矩阵；两个临时探针附件均须在发布前删除。

检查内容：

- Android 用户解锁和系统服务就绪。
- 正式 APK 安装及首页前台状态。
- 首页、翻译项目、设置三页的原始 PNG。
- 游戏更新二级菜单返回设置页。
- `ui` 模式核对启动按钮位于两张卡片之间、竖屏外侧留白、横屏等宽等高卡片、较小平板与大字体布局，以及详情页返回和上下拖动。在云端模拟器临时设置蜂窝网络延迟，观察真实检查请求的固定进度区、滚动和取消，再核对应用/汉化标签的操作隔离与状态保留；结束后恢复网络配置。此项没有下载未来版本 APK，不能写成下载百分比全流程实测。网络模拟使用 [Android Emulator 控制台](https://developer.android.com/studio/run/emulator-console) 的标准命令。
- 内置容器 Google 设置入口，不添加账号或发起交易。
- 平板竖屏单列、宽横屏双列的实际页面位置。
- Android 15 Experimental 16 KB 镜像的 ABI、页大小及 ARM64 发行包运行条件。

`report.json` 记录实际发行版本、APK 摘要、系统 ABI、页大小、Native Bridge 及已通过项目。失败会保留原因，不把模拟器启动标志当作应用运行成功。16 KB 镜像没有 ARM64 ABI 时只记录环境不支持，不安装 APK，也不记为应用测试通过。

`package-queries` 模式仅检查应用身份查询：Android 11 与 Android 17 使用实际生产
PackageManager 代理和临时包记录，覆盖未知/已卸载 UID、共享 UID、列表与单包身份、
签名比较、版本限定查询及诊断失败不影响原调用。记录和虚拟客户端身份在 `finally`
中恢复，不安装或启动游戏，不读取账号；该结果不能作为 70036 已修复的证明。
权限回归另从独立访客进程调用 Android 公开 PackageManager / Context，跨 Binder
读取服务进程的临时注册表；比较绑定前的真实系统结果与绑定后的容器权限及元数据。
完成后恢复客户端身份并清理注册表。该检查用于发现只调用内部服务时遗漏的框架入口。

截图取自未改动的正式 APK。系统栏图标在模拟器中隐藏，直接保存原始 PNG，不修改应用像素或注入业务状态。截图必须经人工核对后才能放入 README，不会自动发布。

界面检查保留实际系统导航，分别切换手势导航、三键导航、深色模式和横屏，从系统窗口记录读取导航区域，核对二级页的返回、关闭和底部操作不与导航栏重叠。横屏使用真实屏幕旋转，先检查正文可见，再滚动到操作区；不以改变宽高代替旋转。背景衔接及图标对比度通过原始截图核对；检查后恢复模拟器原有导航及旋转模式。

Android 11 x86_64 的 ARM 翻译环境只用于运行基线，不代表 ARM64 原生设备或 16 KB 兼容性。该工作流不操作真实商品或付款，不证明 Google 登录、结算、扣款或到账成功。支付策略单元测试、Android 回调测试和真实购买应分别报告。

Experimental 16 KB x86_64 镜像属于用户空间模拟，不能代替 ARM64 原生 16 KB 设备。Google Play Billing Lab 的响应模拟需要应用开发者配置与许可测试账号；启动器不能替游戏取得这些权限。

## 已记录的运行结果

[构建 54 的云端记录](https://github.com/gravere/BYBUS/actions/runs/40724375539)使用同一份签名 APK 检查了 Android 11 / 4 KB 和 Android 15 Experimental 16 KB。安装、首页、项目与设置页、二级返回以及平板横竖屏检查均通过；此前后台同步的精确闹钟权限异常未再出现。

Google 容器入口仍未通过：Android 11 的错误栈位于 ARM 翻译层，16 KB 实验镜像仍有 Google 进程异常和 Binder 连接失败。因此工作流的成功状态仅表示运行基线完成，必须同时阅读 `google_component_ui`、`payment_runtime` 和崩溃记录，不能将其解释为登录或付款成功。
